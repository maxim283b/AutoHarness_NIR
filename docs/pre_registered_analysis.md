# Предварительно зарегистрированный план анализа

**Версия:** 1.0, 8 октября 2026 г.  
**До фиксации этого файла реальные `heldout`-исходы не просматриваются.**

## 1. Гипотезы и единица анализа

Единица анализа — одна задача `task_id` при одном harness, seed и конфигурации
target-модели. Harness — внешняя схема работы агента: инструкции, порядок шагов,
правила инструментов, проверка, исправление, память и остановка. Веса target-модели
и verifier фиксированы. Held-out не используется для выбора коэффициентов, моделей,
порогов, признаков или алгоритмов.

Основные гипотезы:

* H1: существует гетерогенность: выбор harness даёт практически значимый выигрыш
  против лучшего fixed harness хотя бы на части задач;
* H2: признаки задачи позволяют предсказывать reward лучше базовой стратегии;
* H3: этот сигнал сохраняется по новым шаблонам задач и seed, а не только внутри
  случайно перемешанного split;
* H4: при равном числе task-evaluations контекстный bandit не ухудшает success и
  улучшает held-out reward.

Разделение делается по `task_template` (семейство/шаблон задачи), а не простым
случайным split. Рекомендуемые роли: `search`, `validation`, `online`, `heldout`.
Если шаблон встречается только в одном split, это ограничение переносимости, а не
повод переименовать его постфактум.

## 2. Награда и заранее выбранные чувствительности

Основная функция:

```text
reward = success - lambda_tokens * tokens / 1000 - lambda_tools * tool_calls
```

Latency не входит в reward: сначала измеряется её стабильность. Основная точка
анализа: `lambda_tokens=0.10`, `lambda_tools=0.02`. Дополнительные точки:

* low-cost: `(0.05, 0.01)`;
* high-cost: `(0.20, 0.05)`;
* quality-first: `(0.00, 0.00)`.

Это чувствительность, а не выбор лучшей точки после просмотра held-out. Если
`tokens` или `tool_calls` отсутствуют, строка считается невалидной; missing не
заменяется нулём. `success` — бинарный результат одного frozen verifier.

## 3. Основные сравнения и практическая значимость

Для каждой точки reward сначала агрегируется по задаче, затем сравнивается
парно между harness на общей матрице задач. Основной эффект — средняя разница
`selected - best_fixed` на задаче; CI — cluster bootstrap по `task_id` (10 000
репликаций, seed 20261008), с сохранением всех строк одной задачи внутри кластера.

Практически значимая разница заранее равна **0.05 reward** или **2 процентным
пунктам success** при неухудшении tokens/tool calls. Дополнительный экономический
критерий — не менее 5% снижения tokens или tool calls при одинаковом success.
Статистический тест сам по себе не превращает малый эффект в практически важный.
Все CI — 95%, двусторонние; при множественных парах это описательный анализ,
без post-hoc выбора «победителя».

## 4. Oracle gap и победители

Для задачи `i`:

```text
oracle_gap_i = max_h reward(i,h) - mean_i reward(i,h_fixed_star)
```

где `h_fixed_star` — лучший harness по search/online split, выбранный без held-out.
В отчёте также показываются верхняя граница `max_h reward(i,h)` и средний gap.

Harness считается практически лучшим на задаче, если его reward не более 0.05 ниже
задачного максимума; уникально лучшим — если он единственный максимум после
округления с допуском `1e-12`. Доля задач каждого типа победителя считается с
одинаковым знаменателем; ties не скрываются.

## 5. Seeds и предсказуемость

Повторные запуски считаются независимыми единицами `(task_id, seed)`. Для
каждой такой единицы требуется ровно одна строка каждого harness. Нельзя
объединять seeds словарём по одному `task_id`: сначала анализируются пары
`task_id, seed`, а task-level агрегат при необходимости получается отдельным
усреднением по seeds.

Seed является обязательным полем и логируется в конфигурации и траектории.
Стабильность оценивается как: (a) SD и CI эффекта по seed; (b) доля seed, где
порядок harness совпадает с основным порядком; (c) внутриклассовая корреляция
reward между seed, если повторены те же задачи. Нельзя считать один seed
доказательством устойчивости.

Предсказываются только исходы, доступные до запуска:

1. multinomial logistic regression для выбора лучшего harness;
2. decision tree с `max_depth=3`;
3. отдельная модель ожидаемого reward для каждой пары task-harness.

Сравнение с majority/best-fixed baseline. Модели обучаются только на train folds,
а hyperparameters фиксированы заранее (логистика `C=1`, дерево `max_depth=3,
min_samples_leaf=5`, pair model ridge `alpha=1`). При наличии scikit-learn
используется `GroupKFold` по `task_template`; при недостатке групп анализ явно
помечается как невозможный, а не заменяется случайным split. Calibration —
разбиение вероятностей на 10 заранее заданных bins, Brier score и ECE.

## 6. Метрики

Обязательные: success, reward, tokens, tool calls, cumulative regret относительно
лучшего fixed и task oracle, held-out quality, calibration, 95% CI. Для bandit
cumulative regret строится по online-порядку и одинаковому числу evaluations;
latency только описывается (median, p90, seed CV) до отдельного решения.

## 7. Go/no-go

* **Неконтекстный bandit — go**, если при 25 или 50 evaluations held-out reward
  превышает random и не уступает best fixed более чем на 0.02, success не ниже
  более чем на 1 п.п., а CI эффекта не противоречит нулю критически; иначе no-go.
* **Contextual bandit — go**, если выполняется тот же критерий и есть минимум
  0.05 oracle gap, либо предсказатель beats best-fixed на >=0.02 held-out reward
  на шаблонах, не виденных при обучении. Иначе сначала не расширять RL.
* **Автопоиск одной схемы — go**, если найденный fixed harness улучшает held-out
  reward на >=0.05 либо success на >=2 п.п. при не худшей стоимости в равном
  бюджете evaluations. Иначе считать сигналом поиск не подтверждённым.
* **Перенос между доменами — go**, если на новом домене при 5/10/25/50
  наблюдениях перенос достигает того же порога минимум на 5 evaluations раньше
  обучения с нуля и не теряет более 1 п.п. success.

Эти пороги и коэффициенты не меняются после открытия held-out. Окончательное
решение сопровождается CI, размером эффекта и числом evaluations.

## 8. Размер разведочного этапа

План: 40 задач на домен, минимум 4 harness и 3 seed для 20 повторных задач.
Для оценки доли победителя с точностью около ±0.15 нужен порядок 40 задач; это
разведочный, не confirmatory размер. При меньшем числе задач отчёт помечается
`underpowered`. Для обнаружения парного эффекта 0.05 при SD разностей 0.20 и
мощности около 0.80 потребуется примерно 63 независимые задачи; шаблонная
зависимость уменьшает эффективный размер, поэтому это ориентир, а не гарантия.

## 9. Анализ отрицательного результата

Сначала проверяются целостность JSONL, баланс harness, пропуски, детерминизм,
leakage шаблонов и verifier invariance. Затем разделяются причины: нет
гетерогенности, есть gap но нет предсказуемости, есть предсказуемость но мало
данных, reward конфликтует с quality, либо перенос ломается. Отрицательный
результат не компенсируется подбором lambda, feature engineering или порога по
held-out. Допускается только заранее указанная чувствительность и bootstrap.
Практический вывод при no-go: выбрать одну компактную схему и/или условную
эскалацию после ошибки verifier; RL и дорогой поиск отложить.

## 10. Стандартизированный JSONL

Обязательные поля строки:

```json
{"task_id":"t1","task_template":"strings-v1","split":"search",
 "seed":0,"harness":"direct","model":"frozen-model@sha256:…",
 "success":1,"tokens":321,"tool_calls":0,"latency_s":1.2,
 "task_features":{"n_words":4,"has_edge_case":1},
 "trajectory":[{"step":"solve","input_hash":"…","output_hash":"…"}]}
```

`split` допускает `search`, `validation`, `online`, `heldout`; `task_features`
должен содержать только признаки, известные до запуска. Полная `trajectory`
обязательна даже если анализатор её не разворачивает. Конфигурация модели,
harness и seed не должны молча меняться внутри файла.

## 11. Воспроизводимость и безопасность

Скрипт принимает явный `--seed`, сохраняет параметры запуска и не перезаписывает
существующий отчёт без `--overwrite`. Синтетический пример — единственный тест
этой реализации на текущем этапе. Реальные held-out данные подключаются лишь
после того, как этот файл зафиксирован в version control/рабочем журнале.
