# Предварительные выводы по вопросам НИР

1. **Существенна ли разница между фиксированными протоколами?** По качеству в реальном пилоте из двух test-задач — нет наблюдаемой разницы, все 2/2. По затратам разница велика: P1 в среднем 184 токена и 1 вызов, P4 — 762 токена и 3 вызова. Это результат конкретных двух простых задач, не доказательство общего равенства качества.
2. **Лучше ли динамический контроллер фиксированного?** Здесь нет: ни один метод не улучшил успех относительно P1, выбранного по train; LLM-контроллер добавил 186 токенов на задачу. При `n=2` нельзя заключать, что контроллер бесполезен вообще.
3. **Лучше ли переключение, чем выбор в начале?** Не установлено: на обеих test-задачах видимая проверка прошла сразу, switch count = 0 у всех. Rule и rule_front_only совпали по исходам и токенам.
4. **Помогает ли история?** Не обнаружено: обученный и холодный LinUCB оба выбрали дешёвый P1 и дали 2/2. Две train-задачи для сравнительного пилота крайне мало; отдельная диагностика P1 на 12 train-задачах дала 12/12 без ошибок, то есть полезного обучающего сигнала для переключений не возникло.
5. **Какие протоколы выбираются для разных типов задач?** Пилот содержит только Python-кодирование. Лексические признаки (длина, list, tree, math) записываются, но вывод о междоменных предпочтениях невозможен.
6. **Окупается ли контроллер?** На этих двух задачах нет: LLM-контроллер увеличил расход с 184 до 370 токенов в среднем без выигрыша в успехе. Денежная цена API для локального LM Studio равна нулю, но вычислительное время и энергия не бесплатны; энергия не измерялась.
7. **Какие проблемы возникли с состоянием?** Критичны перенос предыдущего кода, ошибки видимого теста, плана, замечания reviewer и истории событий. Тест на P1 → P3 → P4 показывает, что они не теряются. Перезапись harness во время задачи не выполняется.
8. **Насколько идея отличается от аналогов?** Общая адаптивная координация не нова: MaAS выбирает архитектуру под запрос, DyFlow меняет workflow по feedback, Symphony-Coord применяет LinUCB, TRACER управляет ходами. Отличие пилота — контролируемая проверка переключения между четырьмя фиксированными протоколами при единой модели, состоянии и evaluator, с учётом overhead. Это экспериментальная постановка, а не заявка на принципиально новый метод.
9. **Есть ли основания продолжать НИР?** Да, но сначала нужен benchmark с достаточной частотой наблюдаемых промежуточных ошибок и возможностью их исправить. Текущий результат показывает, что на простых задачах дополнительные роли быстро проигрывают по затратам, а гипотеза о switch остаётся непроверенной. Продолжение полного плана на этом же срезе было бы слабой тратой ресурсов.
10. **Что улучшить далее?** На новом train/validation подобрать заранее определённый, более трудный benchmark, затем оценить на нетронутых 20–40 test-задачах; использовать более быстрый LM Studio backend или сократить генерацию ролей; добавить настоящую изоляцию сгенерированного кода; расширить train для LinUCB и проверить чувствительность к штрафу затрат; повторить с несколькими seed/моделями.

Отрицательный результат после реального запуска следует сохранить как результат, даже если ни один dynamic controller не выиграет у лучшего фиксированного протокола.
