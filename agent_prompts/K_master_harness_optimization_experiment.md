## Главная постановка

Исследуется **не динамический выбор одного из заранее заданных harness для каждой задачи**. Главный объект — автоматическое создание и улучшение самого agent harness: системной инструкции, протокола рассуждения, правил применения инструментов, проверки, исправления, памяти, остановки и распределения контекста.

Нужно проверить гипотезу:

> Альтернативный алгоритм поиска по пространству harness-конфигураций способен при одинаковом экспериментальном бюджете получить качество базового AutoHarness/AutoSaddler-подобного метода на более слабой frozen-модели, с меньшим контекстом или с меньшим числом обучающих задач.

Frozen-модель — модель с неизменяемыми весами. Никакого fine-tuning, то есть дообучения весов, не выполнять. Оптимизируется только harness.

Ранее выполненный `H_low_data_policy_selection` используй только как разведочный источник инфраструктуры и сигналов. Не выдавай его за основной эксперимент и не делай per-task routing — выбор отдельного harness для каждой задачи — главным методом.

## Этап 1. Актуальный поиск открытых методов

Проведи поиск в интернете и по открытым репозиториям. Используй прежде всего первичные источники: статьи авторов, официальные репозитории и документацию. Установи точные названия, ссылки, лицензии, доступность кода и дату последнего существенного обновления для:

- GEPA;
- MIPROv2;
- других актуальных методов автоматической оптимизации prompt/program/agent scaffold, применимых к созданию harness.

Отдельно разберись, что пользователь мог иметь в виду под `Tail RL`. Не придумывай алгоритм. Если нет однозначно идентифицируемого метода с таким названием, явно зафиксируй неоднозначность и реализуй **tail-aware objective** — целевую функцию с акцентом на худшие 10–20% задач — как проверяемую альтернативу обычной оптимизации среднего качества.

Результат поиска сохрани в:

- `docs/current_harness_optimization_methods.md`;
- `docs/current_harness_optimization_methods.csv`.

Для каждого метода укажи: что он меняет, какой алгоритм поиска применяет, нужен ли отдельный proposer — модель, предлагающая изменения, — открыт ли код, можно ли честно воспроизвести локально и почему он включён или исключён из пилота.

## Этап 2. Исправь методические проблемы предыдущего этапа

До нового эксперимента:

1. Не обучай кодировщик признаков на validation-задачах. Любые словари, нормализация и статистики вычисляются только по search/train.
2. Для бюджета 0 не называй случайный холодный старт `best fixed`. Либо зафиксируй arm заранее по независимым данным, либо явно назови метод `uninformed cold start`.
3. Доверительные интервалы по случайным replay seeds называй именно интервалами по порядку/случайности алгоритма. Для переноса на новые задачи добавь bootstrap по task units — повторную выборку задач с возвращением.
4. Не используй выводы H для выбора коэффициентов новой целевой функции после просмотра validation. Коэффициенты и критерии остановки зафиксируй до оптимизации.

Добавь регрессионные тесты на эти требования.

## Этап 3. Единое представление harness

Создай сериализуемый `HarnessGenome` или эквивалентную структуру. Genome — набор изменяемых параметров кандидата. Минимальные поля:

- `system_prompt` или идентификатор шаблона;
- `pattern`;
- `planning_mode`;
- `max_repairs`;
- `memory_k`;
- `use_visible_verifier`;
- `verifier_trigger`;
- `stop_rule`;
- `tool_policy` только на уровне разрешённых правил вызова;
- `context_budget`;
- `generation_max_tokens`.

Запрещено изменять:

- hidden tests и ответы;
- `reference_sql`;
- Python sandbox;
- SQL authorizer;
- код verifier;
- веса target-модели;
- содержание benchmark после фиксации manifest.

Реализуй:

- каноническую сериализацию и hash каждого кандидата;
- валидацию допустимости;
- детерминированные mutation operators — операторы изменения;
- журнал родителей и потомков;
- кэш оценки `(candidate_hash, task_id, seed, model_config_hash)`;
- resume без дубликатов;
- раздельный учёт target calls и proposer calls.

## Этап 4. Методы сравнения

Главное сравнение должно быть между алгоритмами **автоматического построения одного фиксируемого harness**, а не между алгоритмами выбора harness на каждой задаче.

Обязательные методы:

1. `seed_harness` — исходный неизменённый harness.
2. `random_mutation_search` — случайный поиск допустимых изменений.
3. `baseline_framework` — максимально близкий воспроизводимый AutoHarness/AutoSaddler-подобный открытый метод. Если точная реализация недоступна, создай честно обозначенный `literature_inspired_baseline`, перечислив отличия от оригинала.
4. `bandit_mutation_operator` — bandit выбирает тип следующей мутации, но итогом остаётся один замороженный harness. Bandit — алгоритм, который распределяет пробы между операторами по их прошлой полезности.
5. Один малоданный последовательный оптимизатор: выбери между эволюционным поиском, байесовской оптимизацией или RL после короткого обоснования по фактической доступности данных. Не называй метод RL, если он не обучает policy последовательного выбора изменений.
6. Для выбранного лучшего оптимизатора сравни обычную среднюю цель и `tail-aware` цель, учитывающую нижний квантиль качества.

GEPA можно использовать как дополнительный baseline, если существующий адаптер проходит smoke и его бюджет можно честно сопоставить. Не включай одновременно GEPA, MIPROv2 и другие тяжёлые методы только ради количества: приоритет — завершённый честный пилот.

Основной reward:

`success - 0.10 * tokens / 1000 - 0.02 * tool_calls`.

Latency — задержку — логируй, но не включай в reward. Добавь ресурсные показатели: context budget, target calls, proposer calls и суммарные токены.

Tail metric зафиксируй заранее. Предпочтительный вариант: среднее reward худших 20% task units. Если задач слишком мало, используй заранее описанную устойчивую замену и не меняй её после запуска.

## Этап 6. Малый, но законченный эксперимент

Работай через LM Studio:

- chat endpoint: `http://127.0.0.1:1234/v1/chat/completions`;
- target по умолчанию: `ministral-3-8b-instruct-2512`;
- target frozen;
- одновременно только один массовый процесс, чтобы не перегружать LM Studio.

Перед каждым реальным этапом проверь `/v1/models`. Если LM Studio недоступна или нужная модель не загружена, не подменяй её другой и не фабрикуй результаты: сохрани готовый код, manifests, команды продолжения и явный статус `blocked_lm_studio`.

Пилот проводи ступенчато:

### Smoke

- 3–5 задач;
- все методы хотя бы один раз проходят полный цикл;
- проверяются логи, budget accounting, отсутствие hidden leakage и resume.

### Основной минимальный запуск

- один основной домен, выбранный до просмотра результата по критерию надёжности verifier;
- режимы 10 и 25 search-наблюдений;
- context budget 2048 и 4096 токенов, если модель и сервер действительно позволяют это контролировать;
- одинаковый лимит task-evaluations для каждого метода;
- рекомендуемый начальный лимит: 25 оценок кандидатов на режим и метод;
- минимум 3 явных algorithm seeds там, где есть случайность;
- одна и та же frozen search task sequence внутри сравнения;
- validation только после завершения поиска и заморозки кандидата.

Если полный факторный запуск оказывается чрезмерным по времени, не урезай методы несимметрично. Сначала закончи симметричную минимальную матрицу: 10 observations × один context budget × все обязательные методы. Затем расширяй до 25 observations и второго context budget. Явно различай `complete_core` и `optional_extension`.

### Проверка переноса

Лучшие 1–2 замороженные конфигурации перенеси на второй домен без изменения текста и параметров. Разрешена отдельная оценка, но не дооптимизация по validation второго домена.

### Held-out

Held-out — окончательно отложенные данные — открывай ровно один раз только после:

- заморозки алгоритмов;
- заморозки финальных harness configs;
- создания hashes;
- завершения validation-сравнения;
- записи решения о финалистах.

Если статистической или вычислительной мощности недостаточно, held-out не открывай и оставь его для следующего подтверждающего эксперимента.

## Этап 7. Что измерить

Для каждого метода и режима отчитай:

- success;
- reward;
- tokens;
- target model calls;
- proposer model calls;
- tool calls;
- context budget;
- tail reward;
- worst-task failure rate;
- число уникальных кандидатов;
- число отклонённых и недопустимых мутаций;
- эффективность поиска: улучшение на одну task-evaluation;
- Pareto frontier — набор вариантов, где нельзя улучшить качество без роста стоимости;
- bootstrap confidence intervals по задачам;
- чувствительность к algorithm seed.

Главные вопросы:

1. Получает ли какой-либо метод то же качество при context 2048, что baseline при 4096?
2. Получает ли он сопоставимое качество после 10 задач, что baseline после 25?
3. Улучшает ли tail-aware цель трудные задачи без неприемлемого падения среднего success?
4. Может ли оптимизированный harness слабой модели приблизиться к заранее зафиксированной более сильной reference-конфигурации, если такая модель доступна? Это только дополнительный анализ, не меняющий основное сравнение.
5. Какие компоненты harness изменяются стабильно у разных seeds?

## Правила принятия решений

- Не спрашивай пользователя о мелких инженерных решениях: выбирай разумный вариант и документируй его.
- Спроси только если требуется изменить модель, открыть held-out раньше времени или совершить действие за пределами репозитория.
- Не устанавливай тяжёлые зависимости без необходимости. Предпочитай уже имеющееся окружение.
- Не заявляй преимущество по результату менее чем на 10 validation task units; такие результаты называй только smoke или exploratory.
- Если метод не воспроизводится, честно исключи его и используй literature-inspired baseline вместо имитации оригинала.
- При первом употреблении каждого английского термина дай короткое русское пояснение.
- Во время долгих запусков регулярно сообщай прогресс и обеспечь безопасный resume.
