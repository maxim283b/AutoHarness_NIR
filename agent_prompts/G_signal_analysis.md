## Общие обязательные правила

1. Target-модель была frozen и запускалась через LM Studio; проверь это по config, а не предполагай.
2. Не объединяй результаты разных model id, artifact hash, backend или sampling config.
3. Не меняй reward, пороги, признаки или split после просмотра результатов.
4. Held-out не открывай и не используй. Для решения применяется validation/gate.
5. Независимая единица повтора — `(task_id, seed)`.
6. У каждой единицы должна быть ровно одна строка каждого harness.
7. Инфраструктурные ошибки исключаются из качества агента и показываются отдельно.
8. Latency не входит в reward.
9. Все bootstrap и модели имеют явный seed.
10. Групповая перекрёстная проверка выполняется по `template_group`.
11. Не перезаписывай существующие отчёты.
12. При первом употреблении английского термина поясняй его по-русски.
13. Все выводы должны ссылаться на машинно-читаемые результаты.

## Задача

Строго по предварительно зарегистрированному плану проанализируй Python и SQL runs.

Сначала проверь:

- полноту матрицы `(domain, task_id, seed, harness)`;
- совпадение LM Studio model/config;
- split isolation;
- отсутствие скрытых ответов в model messages;
- отсутствие held-out;
- отсутствие дубликатов resume;
- отделение инфраструктурных ошибок.

Рассчитай:

- success, reward, tokens и tool calls;
- лучший fixed harness — одну общую схему;
- oracle gap — потенциальный выигрыш идеального выбора;
- доли уникально и практически лучших harness;
- устойчивость по seeds;
- зависимость победителя от домена и признаков задачи;
- логистическую регрессию;
- дерево решений;
- модель ожидаемой награды для пары task-harness;
- bootstrap 95% confidence intervals — доверительные интервалы повторной выборкой.

Отдельно сравни:

- Python;
- SQL;
- объединённые данные;
- обучение на Python и проверку на SQL только по общим признакам;
- обучение на SQL и проверку на Python.

## Решение

Запиши ровно одно основное решение в `go_no_go.json`:

- `NO_SIGNAL`: искать один fixed harness;
- `POST_OUTCOME_SIGNAL`: использовать условную эскалацию после verifier;
- `CONTEXT_SIGNAL`: переходить к contextual bandit — выбору с учётом задачи;
- `TRANSFER_SIGNAL`: исследовать перенос между доменами;
- `UNDERPOWERED`: данных недостаточно для решения.

Не объявляй успех только по accuracy предсказания лучшего класса. Основная проверка — улучшение reward относительно best fixed на validation при заранее заданном пороге.
