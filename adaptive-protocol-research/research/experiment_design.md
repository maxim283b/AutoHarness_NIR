# Протокол эксперимента

## Данные и разделение

MBPP-sanitized взят из существующего локального `pilot/data`, который ссылается на `google-research-datasets/mbpp:sanitized`; исходный SHA-256 указан в `../pilot/splits_manifest.json`. В этом пилоте используются первые 12 задач заранее зафиксированного train и первые 20 задач test. ID и SHA файлов записаны в `data/manifest.json`. Поднабор не подбирался по успешности протоколов. Все 32 эталонных решения проходят локальный evaluator.

Агенту показываются формулировка и первый публичный assert; остальные assert используются только после завершения задачи. Истинные ответы и результат скрытой проверки не доступны контроллерам. На каждом логическом этапе есть одна генерация кода и единая видимая проверка. После ошибки допускаются ещё две попытки. Планировщик и reviewer — отдельные вызовы **той же** модели. Смена протокола возможна только между попытками; лимит — два переключения. Состояние, план, код, feedback, critique и события сохраняются.

## Сравнения

1. На train выполняются P1–P4; лучший фиксированный протокол выбирается по числу успехов, затем по сумме токенов.
2. На test выполняются все четыре фиксированных протокола, rule, LLM-controller, LinUCB с train-историей, холодный LinUCB, seeded random и rule с выбором только в начале.
3. LinUCB получает завершённые train-исходы всех четырёх фиксированных запусков. Награда — `success - 0.1 × min(1, tokens / task_token_cap)`: полное исчерпание бюджета оценивается как штраф 0.1 к успеху. Это заранее выбранный компромисс; основной вывод всё равно должен сравнивать успех и токены раздельно. Для переключений LinUCB применяет начальные контексты к более поздним этапам с малой поддержкой данных — существенное ограничение.
4. Test-исходы никогда не подаются обратно в bandit и не используются для выбора гиперпараметров. `alpha=0.5`, признаки и rule зафиксированы до test. Проверка benchmark reference solutions служит только проверкой evaluator.

## Метрики и пределы вывода

Для каждой задачи записываются успех по видимому и скрытым тестам, токены, число LLM-вызовов, число инструментальных проверок, модельная и полная задержка, число переключений, расходы контроллера, ошибки и полная трасса. Поле `errors` — число проваленных видимых проверок плюс ошибка исполнения harness; скрытая ошибка отдельно записывается как `hidden_error`. Денежная стоимость считается лишь при явных тарифах в переменных окружения. Отсутствующие API usage помечаются как приблизительные токены. Для долей используется 95% интервал Wilson, парные расхождения показываются абсолютными числами. Небольшой n и единственный тип задач не дают основания заявлять статистическую значимость или обобщение на другие домены.

Сравнение rule с rule_front_only оценивает пользу переключения в этой политике; оно не делает причинного вывода о каждом отдельном switch. Успех после переключения сопоставляется с контрфактическим запуском на том же ID, но текстовые выводы модели могут расходиться.

## Бюджет и безопасность

CLI оценивает консервативный верхний предел до запуска. По умолчанию на задачу: максимум 12 вызовов, 10 000 токенов, 120 секунд; глобально 2 000 вызовов, 1,5 млн токенов, 7 200 секунд. Полный план — 248 task-runs, верхняя оценка 2 976 вызовов и 2,48 млн токенов, поэтому стандартный полный **реальный** запуск блокируется лимитами. Исполнение реальной модели требует явного `--real-budget-approved` и пересмотренных лимитов. Оплату заранее можно оценить как `input_tokens × input_rate / 1e6 + output_tokens × output_rate / 1e6`; точная цена зависит от провайдера и введённых ставок.

Generated Python выполняется в отдельном процессе с `-I`, timeout и простым AST-фильтром опасных вызовов/импортов. Это не полноценная системная изоляция. Для недоверенного внешнего кода необходим контейнер или VM без сети и с лимитами ресурсов. В этой версии запускать следует только доверенный MBPP-код и контролируемую модель.

## Фактически выполненный реальный мини-пилот

После двух измерительных train-вызовов зафиксированы модель `ministral-3-8b-instruct-2512`, `temperature=0`, пределы генерации по ролям (planner 80, executor 300, verifier 96, controller 64 токена), 10 вызовов / 4 500 токенов / 150 секунд на задачу и 30 минут на весь запуск. Выполнены первые 2 train и первые 2 test задачи во всех десяти arms. Это проверка осуществимости и ориентир по затратам, а не замена запланированного исследования на 20 test-задачах. После неё P1 дополнительно выполнен на всех 12 train-задачах для диагностики трудности benchmark; test-исходы не использовались для изменения rule или bandit-гиперпараметров.
