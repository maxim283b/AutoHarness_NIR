## 1. Исходный научный вопрос

Проверяется следующая гипотеза:

> Можно ли улучшить алгоритм автоматического создания agent harness в существующем AutoHarness/AutoSaddler-подобном фреймворке, заменив его исходный алгоритм поиска на RL, TailRL или другой малоданный оптимизатор, и тем самым сохранить либо повысить качество при более слабой frozen-модели, меньшем контексте или почти полном отсутствии обучающей выборки?

Agent harness — это не только выбор одного готового pattern. Это автоматически создаваемая или изменяемая совокупность:

- системной инструкции;
- протокола планирования;
- правил применения инструментов;
- verifier-протокола, то есть правил проверки;
- исправлений после ошибки;
- памяти;
- правил остановки;
- распределения контекста и бюджета генерации.

Главный объект оптимизации — **сам harness**. Итогом каждого метода должен быть один или несколько автоматически созданных и затем замороженных harness-кандидатов. Динамический выбор между заранее известными `direct`, `self-refine` и другими схемами не является главным экспериментом и не может подменять генерацию harness.

Target-модель — модель, решающая benchmark-задачи, — остаётся frozen: веса не изменяются. Запрещены fine-tuning, LoRA и любое обновление весов.

## 3. Обязательный Gate A: идентифицировать настоящий открытый baseline

До реализации и до новых validation-запусков проведи актуальный поиск по первичным источникам: официальным статьям, документации и репозиториям авторов.

Проверь точные названия и существование:

- AutoHarness;
- Harness AutoSaddler / AutoSaddler;
- BetterHarness;
- GEPA;
- MIPROv2;
- AFlow;
- других открытых методов автоматического улучшения agent scaffold, prompt program или harness.

Для каждого кандидата зафиксируй:

- официальное название;
- статью и официальный репозиторий;
- лицензию;
- что именно метод генерирует или изменяет;
- какой алгоритм поиска использует;
- нужен ли proposer;
- можно ли запустить локально с LM Studio через OpenAI-compatible API;
- можно ли заменить его поисковый алгоритм, сохранив остальную систему;
- подходит ли он для слабой модели и малого числа задач.

Выбери **один конкретный открытый baseline framework**. Приоритет выбора:

1. открытый код и разрешающая лицензия;
2. автоматическая генерация или содержательное улучшение harness/scaffold;
3. отделимый search/optimizer module;
4. возможность одинаково подключить baseline optimizer и альтернативные оптимизаторы;
5. работа через LM Studio либо реализуемый адаптер.

Сохрани решение в:

- `docs/final_baseline_selection.md`;
- `docs/final_baseline_selection.json`.

В JSON обязательно укажи `selected_framework`, `official_repository`, `paper`, `license`, `commit_or_release`, `original_optimizer`, `replacement_boundary` и `reproduction_status`.

### Строгое правило baseline

Нельзя называть собственный упрощённый цикл AutoHarness, AutoSaddler или точным baseline. Допустимы только два статуса:

- `exact_or_adapter_reproduction` — используется официальный код или тонкий адаптер без изменения алгоритма;
- `blocked_no_reproducible_open_baseline` — точное воспроизведение невозможно.

Если Gate A заблокирован, не фабрикуй literature-inspired замену как основной результат. Сохрани доказательства блокировки, предложи следующий наиболее близкий открытый framework и останови **подтверждающую** часть. Можно подготовить код адаптера и smoke, но нельзя заявлять, что исходная гипотеза проверена.

## 4. Обязательный Gate B: точно определить RL и TailRL

До реализации зафиксируй, что именно называется RL и TailRL.

RL — reinforcement learning, обучение с подкреплением, — считается реализованным только если присутствуют:

- состояние, включающее текущий harness и историю оценок;
- действие, изменяющее harness;
- reward после оценки изменения;
- обучаемая policy, выбирающая следующие действия;
- последовательность как минимум из нескольких зависимых шагов;
- обновление policy по собранным переходам или траекториям.

Bandit над операторами мутации не называй RL. Эволюционный поиск не называй RL.

Для TailRL найди конкретную статью, репозиторий или точное определение, которое имелось в виду. Если существует несколько несовместимых трактовок, перечисли их и выбери одну только при наличии первичного источника и реализуемого алгоритма.

Если точный TailRL нельзя однозначно идентифицировать, используй название `tail-aware RL variant`, а не `TailRL`, и реализуй заранее зафиксированную модификацию RL objective, ориентированную на худшие задачи. В отчёте это должно быть явно отделено от воспроизведения опубликованного TailRL.

Сохрани спецификацию в:

- `docs/rl_tailrl_specification.md`;
- `experiments/final_harness_experiment/optimizer_spec.json`.

## 5. Единая граница сравнения

Во всех методах неизменны:

- выбранный baseline framework;
- представление harness либо единый адаптер к нему;
- benchmark;
- task splits;
- verifier;
- target model;
- proposer model для методов, которым proposer необходим;

- количество search task-evaluations;
- лимит target calls;
- лимит proposer calls;

- правила остановки;

Между методами меняется только optimizer — алгоритм, выбирающий следующее изменение harness.

Если исходный framework не допускает такую замену без изменения остальных компонентов, явно задокументируй это как ограничение сравнения.

## 6. Методы обязательного сравнения

Минимальное подтверждающее сравнение:

1. `seed_harness` — исходный harness без оптимизации.
2. `framework_original_optimizer` — оригинальный алгоритм выбранного открытого framework.
3. `random_search` — случайный поиск в том же пространстве изменений.
4. `rl_optimizer` — настоящий RL по приведённым выше критериям.
5. `tail_rl_optimizer` или честно названный `tail_aware_rl_variant`.

Опционально, только если не мешает завершению ядра:

- bandit optimizer;
- evolutionary optimizer;
- GEPA;
- Bayesian optimization — байесовская оптимизация дорогих экспериментов.

Не включай много методов ценой двух-трёх кандидатов на каждый. Лучше пять обязательных методов с достаточным горизонтом, чем десять номинальных методов без обучения.

## 7. Настоящая автоматическая генерация harness

Каждый optimizer должен работать с содержательным пространством изменений. Оно должно включать не только переключатели, но и по крайней мере один автоматически генерируемый текстовый компонент:

- системная инструкция;
- инструкция планирования;
- инструкция проверки;
- правило исправления;
- правило выбора инструмента;
- правило остановки.

Используй proposer model — модель, предлагающую изменения. По умолчанию сначала попытайся использовать ту же локальную модель через LM Studio, чтобы проверить режим с одной слабой моделью. Если это делает генерацию неработоспособной, допускается отдельно зафиксированная более сильная proposer model, но:

- target всё равно остаётся слабой и frozen;
- proposer и target логируются отдельно;
- сравнение «слабая модель самостоятельно улучшает свой harness» и «сильный proposer улучшает harness слабой target» не смешивается.

Proposer не получает hidden tests, reference answers, held-out labels или полный правильный SQL. Допустима только публичная задача и обезличенная обратная связь verifier: класс ошибки, факт успеха, стоимость и безопасное описание проблемы.

Сохраняй полный lineage — происхождение кандидатов, текст изменений, parent hashes и причины принятия.

## 8. Экспериментальные режимы

Работай через LM Studio:

- `http://127.0.0.1:1234/v1/chat/completions`;
- основной target: `ministral-3-8b-instruct-2512`, если он доступен;
- temperature и sampling config фиксируются до запуска;
- target frozen;
- одновременно только один массовый процесс.

### 8.1 Обязательное ядро

Главный домен: SQL с детерминированным verifier, если аудит benchmark не обнаружит критической проблемы.

Минимум:

- 10 search-задач;
- не менее 15 автоматически предложенных кандидатов на optimizer и seed;
- 3 algorithm seeds;
- 10 validation-задач;
- context 2048;
- одинаковый двойной бюджет для optimizer-методов:
  - одинаковое число task-evaluations;
  - одинаковый верхний лимит target calls;
- одинаковый proposer-call budget для методов с proposer;
- validation только после заморозки кандидатов всех методов.

Для `seed_harness` не нужно бессмысленно повторять поиск. Его неиспользованный search budget обозначь отдельно как `not_applicable`, но сравнение validation выполняй на тех же задачах и seeds. Не заявляй равенство search-бюджетов между seed и оптимизаторами.

Если 15 кандидатов × все методы × 3 seeds вычислительно невозможно, разрешён двухступенчатый дизайн, зафиксированный заранее:

1. screening — первичный отсев на 3–5 задачах;
2. successive halving — последовательное сокращение числа кандидатов с увеличением числа задач для выживших;
3. одинаковые правила и бюджет для всех optimizer-методов.

Нельзя уменьшать бюджет после просмотра результатов отдельного метода.

### 8.2 Малоданный режим

После ядра сравни:

- 5 search-наблюдений;
- 10 search-наблюдений;
- 25 search-наблюдений.

Если полный запуск 25 невозможен, завершённые 5 и 10 всё равно должны использовать одинаковую методику. Главный вопрос: способен ли альтернативный optimizer достичь результата original framework при меньшем числе наблюдений.

### 8.3 Короткий контекст

Сравни минимум:

- 2048 токенов;
- 4096 токенов.

Если LM Studio позволяет надёжно выставить 1024, добавь его как стресс-режим. Главный показатель: сохраняет ли оптимизированный harness при 2048 качество original framework при 4096.

### 8.4 Более слабая модель

Если в LM Studio доступна вторая, объективно меньшая или более слабая модель, заранее зафиксируй её как `weak_target` и основную как `reference_target`. Не меняй модель по ходу эксперимента.

Сравни:

- исходный framework на reference target;
- оптимизированный harness на weak target;
- seed harness на weak target.

Не смешивай данные разных моделей в обучении одного optimizer, если transfer не зарегистрирован отдельно.

### 8.5 Перенос на второй домен

После заморозки финальных harness выполни перенос SQL → Python без дополнительного изменения harness. Это дополнительный анализ общности, а не часть выбора финалиста.

### Критерии подтверждения гипотезы

Заранее выбери минимум один основной критерий, например:

- RL validation reward выше original optimizer при сопоставимом success и одинаковом бюджете;
- RL достигает не хуже чем −0.01 success от original framework при 50% меньшем контексте;
- RL с 10 наблюдениями достигает результата original optimizer с 25 наблюдениями;
- tail-aware RL улучшает reward худших 20% задач без падения среднего success более чем на 0.02.

Укажи минимально значимый эффект и доверительный интервал. Не определяй успех постфактум.

## 10. Изоляция данных

- Search используется для обновления optimizer.
- Validation используется только для сравнения замороженных кандидатов.
- Held-out не влияет на пространство поиска, prompts, reward, выбор методов, гиперпараметры и финалистов.
- Held-out открывается один раз только после завершения протокола и заморозки всех решений.
- При недостаточной статистической мощности held-out оставь закрытым.

В model messages запрещены:

- hidden tests;
- `reference_sql`;
- правильные ответы;
- held-out labels;
- приватные поля benchmark.

## 11. Статистика

Отдельно оцени:

- средний success;
- средний reward;
- токены;
- target calls;
- proposer calls;
- tool calls;
- tail reward худших 20% задач;
- число полностью проваленных задач;
- improvement per target call;
- improvement per task-evaluation;
- разнообразие созданных harness;
- долю недопустимых и повторных кандидатов;
- чувствительность к seed;
- Pareto frontier — набор решений без одновременного проигрыша по качеству и стоимости.

Используй paired comparison — попарное сравнение методов на одинаковых задачах. Доверительные интервалы переноса считай bootstrap по task units, а случайность оптимизатора показывай отдельно по algorithm seeds.

Не называй интервалы по трём seeds доказательством обобщения на новые задачи.

10. Только затем малоданные, короткоконтекстные и transfer extensions.
11. Held-out только при выполнении всех условий.

Не переходи к массовому эксперименту, если Gate A или Gate B не пройдены. Не компенсируй отсутствие baseline или RL переименованием упрощённого метода.

## 16. Формат финального ответа

Начни с одного из трёх утверждений:

- «Исходная гипотеза проверена»;
- «Исходная гипотеза проверена частично»;
- «Исходная гипотеза не проверена».

Затем простыми словами ответь:

1. Какой официальный framework был взят за основу?
2. Какой его алгоритм был заменён?
3. Был ли реализован настоящий RL?
4. Был ли воспроизведён настоящий TailRL или только tail-aware вариант?
5. Какой метод создал лучший harness?
6. Смогла ли слабая модель сохранить качество при меньшем контексте?
7. Сколько данных и вызовов потребовалось?
8. Что произошло на худших задачах?
9. Насколько надёжен вывод?
10. Был ли открыт held-out?

После этого укажи отклонения от preregistration, результаты тестов и аудита, а также ссылки на raw logs, final configs, summary и команды воспроизведения.

Главное правило: отрицательный результат допустим и ценен. Недопустима только подмена исходной гипотезы более простым экспериментом с тем же названием.
