# Результаты пилота на 8 октября 2026 года

## Статус

Реальный **ограниченный** пилот выполнен через локальный LM Studio с одной моделью `ministral-3-8b-instruct-2512` и `temperature=0`. В нём 2 train и 2 test задачи, 28 парных task-runs, 48 LLM-вызовов, 11 155 токенов и суммарно 1 065 секунд выполнения задач. Тариф API отсутствует: это локальный запуск, энергетические затраты не измерялись. Полный план 12 train / 20 test **не выполнен**: по измеренной скорости он потребовал бы существенно больше вычислительного времени, а диагностика train показала эффект потолка.

Все методы решили обе задачи. P1 использовал примерно в 4,1 раза меньше токенов, чем P4, при том же наблюдаемом успехе; на таком `n` нельзя утверждать равенство качества в популяции. LLM-контроллер потратил в среднем 186 токенов на выбор, половину своих 370 токенов, и не принёс выигрыша на этих задачах. У rule, обученного и холодного LinUCB и варианта «выбор только в начале» получились одинаковые исходы и затраты по токенам. Различия в задержке этих однотипных запусков не следует интерпретировать как качество алгоритма: влияли прогрев и текущая нагрузка локального inference runtime.

Данные и [график реального пилота](../results/real_paired_2/success_rate.png) сохранены в `results/real_paired_2/`. На двух test задачах не было ни одной видимой ошибки или смены протокола. Поэтому доля задач, где переключение помогло или навредило, **не оценивается**. Парные расхождения с train-selected P1 равны 0 улучшений / 0 ухудшений / 2 без изменений для каждого динамического метода.

## Диагностика пригодности benchmark по train

Чтобы не подбирать эксперимент по test-ответам, дополнительно прогнаны все 12 заранее выбранных train-задач с P1 в тех же лимитах и той же модели: **12/12 решены, 0 видимых ошибок, каждый раз 1 вызов**. Первые две строки переиспользованы из парного пилота; остальные десять записаны в `results/train_p1_diagnostic.jsonl`. Интервал Wilson для 12/12 всё ещё широк (примерно 0,76–1,00), но для маршрутизации важнее то, что на всех этих задачах отсутствовал сигнал, запускающий внутритасковое переключение.

Текущий короткий MBPP-срез слишком прост для проверки динамики у этой модели. Результат **не опровергает** идею на более трудных задачах. Следующий набор следует выбрать и зафиксировать на основе train/validation сложностей, затем оценить на новом нетронутом test; нельзя отбирать «сложные» элементы по исходам текущего test.

Проверен вариант более слабого локального backend: уже загруженный `qwen/qwen3-vl-8b` решил один train-пример с первого вызова за ~65 секунд; этого недостаточно, чтобы считать его полезной заменой для данной оценки. Установленная `phi-4-mini-instruct` не загрузилась в LM Studio: runtime завершился до готовности. Результаты этих измерительных запусков сохранены отдельно и не смешивались с основным сравнением.

Первый пробный P4 с единым высоким пределом 700 выходных токенов для каждой роли истёк по лимиту 120 секунд ещё во время ответа планировщика (0 завершённых вызовов). После введения отдельных пределов для planner/executor/verifier/controller повтор того же train-примера завершился успешно за 3 вызова и ~107 секунд. Этот случай показывает, что бюджет роли необходимо учитывать отдельно, а не только в сумме по задаче.

## Проверка состояния и примеры

- На задаче 98 rule прошёл P1 → P3 → P4 после двух ошибок видимой проверки. Перед каждым switch сохранены предыдущий код, ошибка, план/критика, счётчик токенов, задержка и история событий; конечный успех — false. Это **пример неуспешного переключения в mock**, а не свидетельство вреда dynamic policy на реальной модели.
- `tests/test_harness.py` проверяет вызовы всех четырёх протоколов, сохранение состояния при двух switch, отсутствие скрытого assert в событиях, строгую схему и затраты контроллера, бюджет, checker и bandit.
- Все 32 эталонных решения выбранных train/test задач проходят evaluator. Два стандартных импорта (`array`, `copy`) были добавлены после этой технической проверки. Гиперпараметры контроллеров на test-ответах не настраивались.

## Что нужно для научного результата

Зафиксировать следующий benchmark, где на train есть достаточно много **видимых** промежуточных неудач и шанс исправления, затем получить 20–40 нетронутых test-задач и полный набор paired outcomes. Нужны границы бюджета по фактической скорости LM Studio и, желательно, более быстрый backend. Примеры **успешных реальных** переключений и доли «помогло/навредило» сейчас привести нельзя без выдумывания данных.
