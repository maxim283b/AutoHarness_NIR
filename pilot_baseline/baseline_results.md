## Воспроизводимость

| сравнение | исход задачи различается | финальный код различается | сырой ответ модели различается |
|---|---:|---:|---:|
| `baseline` vs `baseline_rep` | 1 / 50 (137) | 12 | 15 |
| `baseline` vs `baseline_r3` | 1 / 50 (429) | 13 | 16 |

- Критерий из плана («не более 2 из 50 исходов расходятся») **выполнен**.
- Побайтового детерминизма **нет**, хотя `temperature=0` и `seed=0` фиксированы. Каждый повтор меняет ответ модели примерно в 30% задач. Сервер обрабатывал запросы строго по одному (`-np 1`, в `baseline_rep` посторонних запросов не было), так что причина в самом CPU-инференсе llama.cpp. Чаще всего так влияет переиспользование KV-кэша общего префикса prompt. Сам evaluator детерминирован.
- Итог: шум baseline на этом test-наборе составляет примерно ±1 задачу (±2 п. п.). Улучшение harness меньше ~3 задач на 50 от этого шума не отличить. Это стоит учитывать при сравнении с GEPA: делать несколько повторов или увеличивать test.

## Наблюдения (алгоритм и evaluator не менялись)

1. **Repair-шаг почти бесполезен для этой модели.** Repair сработал в 16–17 задачах на повтор, а задачу исправил только 1 раз за три повтора. В `baseline` видимый тест после repair прошёл в 1 случае из 16, и даже тогда скрытые asserts провалились. В 5 случаях из 16 модель вернула тот же код без изменений.
2. **B0 Direct против baseline: 0.56 против 0.62, но repair к этой разнице отношения не имеет.** Все три задачи, где baseline выиграл (102, 411, 429), он решил ещё на шаге SOLVE, без repair. Разница объясняется недетерминизмом SOLVE (см. выше), а не repair-циклом. Вклад repair на этом наборе ≈ 0.
3. **Сообщение об ошибке для repair малоинформативно.** Почти все провалы — это `AssertionError` на видимом тесте (15 из 19 в `baseline`). Repair получает только текст assert и `AssertionError`, без фактического значения функции. Это вероятная причина пункта 1 и естественная цель для следующего этапа (GEPA меняет prompts, но не содержание feedback). По заданию здесь ничего не менялось.
4. **Профиль провалов в `baseline` (19 задач):** 16 не прошли видимый тест (15 `AssertionError`, 1 `TypeError`), 3 прошли видимый, но не прошли скрытые. Таймаутов, ошибок harness и обрезаний по `max_tokens` нет: все 66 ответов завершились с `finish_reason=stop`.
5. **Модель подходит для пилота по уровню.** pass@1 ≈ 0.6 попадает в коридор 20–80% из плана, менять размер модели (0.5B или 3B) не нужно.
6. **Стоимость:** ~285 target-токенов и ~1.3 LM-вызова на задачу. Прогон 50 задач на свободном CPU занимает 3–4.5 минуты.

## Где лежат данные

`runs/<run_id>/` для каждого прогона содержит:

- `config.json` — конфигурация harness, candidate, digest модели, версии, SHA манифеста, task id;
- `results.jsonl` — task id, ответ, verifier result, tokens, latency, seed, harness config и trajectory;
- `results.csv` — то же без trajectory;
- `trajectories.jsonl` — отдельные LM-шаги;
- `summary.json` и `run.log`.

`baseline`, `baseline_rep` и `smoke` получены кодом из этой папки, когда он ещё лежал в `../pilot/`: другая сессия перезаписала его позже. Код восстановлен без изменений. Манифест сплитов и SHA данных совпадают побайтово, а повтор `baseline_r3` из новой папки дал тот же результат в пределах шума.

## GEPA, seed 0, локальный teacher `qwen2.5-coder:7b` (`runs/gepa_s0`, `runs/gepa_s0_test`)

**Настройки:** `max_metric_calls=400`, `reflection_minibatch_size=3`, отбор `pareto`, `round_robin`, `cache_evaluation=True`, `seed=0`. Target и decoding те же, что в baseline. Teacher — `qwen2.5-coder:7b` Q4_K_M (digest `dae161e27b0e…`), `max_tokens=2048`, `num_ctx=8192`. **Это результат с локальным teacher, не с API-моделью из плана.**

| | seed (baseline) | best GEPA (кандидат №6) |
|---|---|---|
| val, 20 задач (выбор кандидата) | 0.75 | **0.80** (+1 задача) |
| test, 50 задач | 0.62 / 0.64 / 0.60 (3 повтора) | **0.60** (30/50) |
| токенов target на задачу (test) | 283 | **866** (×3.1) |
| длина prompts, символов (solver / repair) | 141 / 125 | 2205 / 1530 |

**Парное сравнение на test** (GEPA против каждого повтора baseline; bootstrap 10 000 ресэмплов, точный McNemar):

| против | разница pass@1 | 95% CI | решила только GEPA / только baseline | McNemar p |
|---|---:|---|---|---:|
| `baseline` | −0.02 | −0.12 … +0.08 | 3 / 4 | 1.00 |
| `baseline_rep` | −0.04 | −0.14 … +0.06 | 2 / 4 | 0.69 |
| `baseline_r3` | 0.00 | −0.10 … +0.10 | 3 / 3 | 1.00 |

**Ход оптимизации:**

- 57 итераций, 404 metric calls, 7 кандидатов (принято 6 из 31 предложения).
- В 26 итерациях reflection пропущен, потому что все 3 задачи minibatch уже решены.
- 25 предложений отклонены на minibatch: «2/3 не лучше 2/3».
- Затраты teacher: 31 вызов, 32.9k prompt и 21.3k completion токенов, в среднем 163 с на вызов, 1 ответ обрезан по `max_tokens`.
- Общее время 2 ч 51 мин на CPU, параллельно с нагрузкой другой сессии на тот же сервер Ollama.

**Вывод по критериям go/no-go из плана: no-go.**

- На val кандидат чуть лучше seed, но это всего +1 задача из 20, в пределах шума.
- На test улучшения нет: разница от −0.04 до 0.00, CI захватывает ноль с обеих сторон.
- Токены выросли в 3.1 раза при допустимом пределе ×2.

**Разбор качества reflection** (по `reflection_calls.jsonl` и `candidates.json`):

1. Teacher 7B не обобщает, а переписывает конкретный пример. Solver prompt лучшего кандидата содержит выдуманную задачу (`sum_lists`) и требования к ней, которые к MBPP не относятся: «raise ValueError при разной длине», «TypeError при нецелых». Это шаблонная простыня, а не правила решения.
2. В repair prompt вшит готовый ответ train-задачи 801 (`test_three_equal`). Утечки test-задач нет: проверено по именам функций всех 100 задач, единственное совпадение со словом `sum` случайное.
3. Сигнал для отбора слабый. Minibatch из 3 задач при pass ≈ 0.7 почти всегда даёт 2/3 или 3/3, а `strict_improvement` такие предложения отвергает. Val из 20 задач различает кандидатов с шагом 5 п. п., что меньше шума повторов.
4. Повторим вывод baseline: модель repair почти не использует (у GEPA 1 успешный repair из 18), а feedback по-прежнему содержит голое `AssertionError` без фактического значения.

## Что делать дальше

- Повторить с сильным API-teacher (как в плане, `anthropic/claude-sonnet-5-5`): это главный неисследованный фактор. Остальное без изменений, для сравнимости.
- Увеличить разрешающую способность оценки: test на все 257 задач и/или несколько повторов на кандидата, val больше 20.
- Не перебирать дальше gepa-гиперпараметры на 7B-teacher: по этому прогону bottleneck — качество предложений, а не бюджет.
